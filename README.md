# AtlasOps AI

Evidence-driven operations for cloud and private infrastructure. FastAPI + PostgreSQL + Celery/Redis + React/TypeScript. AI can investigate and recommend; a human must explicitly approve every supported infrastructure change. The only execution handler in this release changes an explicitly synthetic database sandbox. Real infrastructure mutation handlers are disabled.

## Start development

Requires Python 3.12+, `uv`, Node 24, npm, Docker with Compose 2.24.4+. From the repository root:

```bash
bash scripts/install.sh
.venv/bin/python scripts/local_services.py start
```

The installer creates a private, ignored `.env` with random **development-only** database/authentication credentials, preserves an existing `.env`, installs hash-locked Python dependencies and npm lockfile dependencies, starts PostgreSQL/Redis, runs Alembic migrations, seeds an explicitly labeled demo tenant, and builds the web app. It does not provision external infrastructure.

The native development processes use API port 8000 and Vite port 5173. Sign in as `administrator@atlasops.local` using the `ATLAS_DEV_AUTH_SECRET` in your private local `.env`. Other seeded roles: `operator`, `approver`, and `viewer` at the same domain. Development authentication intentionally shares the local bootstrap secret; it is not a production identity system. Production rejects development authentication and requires OIDC.

Process control: `scripts/local_services.py start|stop|restart` using the virtualenv Python. It checks API readiness and the frontend response, stores logs/PIDs in `.local`, and only manages processes belonging to this checkout. Each cloud task is isolated: use the existing checkout, not a new worktree.

## Try the complete sandbox workflow

1. Open Incidents and ingest a **synthetic alert**.
2. Collect evidence / request an investigation. Without a configured LLM, the result explicitly states AI is unavailable and presents authorized evidence without inventing a root cause.
3. Propose sandbox recovery with evidence and the resource's exact revision.
4. Review the canonical plan in Approval inbox, confirm explicit approval, then separately confirm execution.
5. A worker revalidates membership, environment/resource scope, policy, hash, expiry, preconditions and the unused decision. It verifies persisted target state and records the outcome.
6. Generate a report for the relevant date. Reports show coverage limits and remain available if email fails.

To run another synthetic scenario while preserving prior results, `seed-scenario` creates a new isolated demo tenant and prints its development identity metadata. Production-impacting deployment, restart, scaling and configuration operations return unsupported; they are not silently simulated.

## Verification

```bash
.venv/bin/pytest backend/tests
.venv/bin/ruff check backend connectors scripts
.venv/bin/ruff format --check backend connectors scripts
.venv/bin/alembic -c backend/alembic.ini check
npm --prefix frontend run build
npm --prefix frontend run test:e2e
```

Backend tests use a separate local PostgreSQL database named `atlasops_test`; never point the test configuration at a production server. Browser tests require running API/worker/scheduler/web, a private local `.env`, and Chromium (`PLAYWRIGHT_CHROMIUM_EXECUTABLE` can override `/usr/bin/chromium`). They provision a fresh explicitly synthetic tenant for repeatability. Tests use local HTTP/SMTP doubles and AWS SDK stubs; see the implementation status for live-system evidence.

## Container workflow

```bash
python3 scripts/dev_env.py
docker compose build api web
docker compose up -d --wait db redis
docker compose --profile app run --rm api alembic -c backend/alembic.ini upgrade head
docker compose --profile app run --rm api python -m atlasops.cli seed
docker compose --profile app up -d --wait
```

Stop native processes first if using the default container ports. The Compose app exposes port 8080 for the web server and 8000 for the API, both on loopback; PostgreSQL/Redis also bind loopback. Use a TLS ingress and managed secrets for deployment. Docker build environments behind a proxy need the trusted CA and proxy DNS supplied, as described in [operations](docs/operations.md). Never disable TLS verification.
